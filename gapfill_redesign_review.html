Inconsistent with your rule

3a's own "preferred source report" guess doesn't use T+2/T+3 — only the real Step 2/3 does

There are, today, two different implementations of "which report could supply this gap year":

  • gapfill_lib_core.py's build_candidates — the one that actually runs, correctly T+2 → T+3.
  • 3a_gapfill_1_build_panel_gap_flags.py:289-318 — a second, independent guess baked into Step 1's output (preferred_source_report, fill_status), which searches every report for the country (any year, not just T+2/T+3) and picks the chronologically earliest one with a matching actual column. It exists purely as an early, no-API-cost preview before you commit to Step 3.

These two can disagree — e.g. 3a might point you at a T+5 report has as "preferred" while the real run won't look past T+3 at all. I'd fix this one of two ways (both cheap):

  1. Align it: make 3a's guess use the same T+2→T+3, latest-date-first rule, so the Step 1 preview is an honest forecast of what Step 2/3 will actually try.
  2. Demote it: keep 3a's broader "is this year visible anywhere" scan as background information (useful on its own — e.g. "no report ever shows this year as actual, so Step 3 isn't going to find it either"), but rename the field so it's clearly not a prediction of the real candidate (e.g. any_report_has_actual_column rather than preferred_source_report).

I'd lean towards (1): it's a small change (reuse build_candidates inside 3a instead of the separate loop) and it means there's exactly one place that encodes "what counts as a candidate report."

Output contract: one Source Category column, real report names kept

Superseding what I proposed earlier (a synthetic per-gap-year report id, plus a separate is_gap_fill boolean) — your design is cleaner and I'm adopting it instead:

  • Report-identity columns (json_file, pdf_file_name, …) keep their current names and get the real source PDF — the actual T+2/T+3 report, not a made-up name — because a later step may need to go back and read other things from that same PDF.
  • last_actual_year → year, but only at the point where gap-fill's output is appended to the three-round table — the three-round table itself keeps calling it last_actual_year until that append happens, at which point both sides get renamed together.
  • One new column, Source Category, with exactly three values: Machine Running, Human Review, Gap Fill. Gap-fill only ever writes Gap Fill — tagging existing rows as Machine Running vs. Human Review is your teammate's merge step, not something gap-fill's code needs to know how to do.
  • Everything else about a gap-fill row (country, top_category, hierarchy_id, level, parent_label, label_verbatim, value, publication date read the same way Step 1 reads it, …) is schema-identical to a normal extraction row — no new audit-only columns added to the final table (the rich audit detail — offset, candidate list, validation errors — stays in gap-fill's own working files: gapfill_resolution, gapfill_attempts — it was never meant to land in the final panel).
New: a real bug this design surfaces

Reusing the real report name breaks 3a's current "one row per report" dedup

This is the one consequence of keeping real report names that I don't think either of us had spelled out yet. 3a_gapfill_1_build_panel_gap_flags.py:122 (build_report_table) starts with df.sort_values("json_file").drop_duplicates("json_file", keep="first") — it assumes json_file alone identifies one report-level row. Once a real report can legitimately carry two row-groups — its own normal extraction at its own last_actual_year, and a gap-fill row-group at an earlier year it also happened to supply — that assumption breaks: drop_duplicates("json_file") would silently keep only one of the two and discard the other.

Practically, this also means the row-level unique key isn't quite country + report + hierarchy on its own once gap-fill is folded in — it needs year as a fourth dimension (country + report + year + hierarchy), since the same report can now appear at more than one year.

Proposed fix: change every place that currently dedupes/groups by json_file alone (3a's report-table build, and the panel/coverage-matrix construction that follows it) to group by (json_file, year) instead. Flagging this now rather than after it quietly drops data on a future re-run.

Missing deliverable

Step 2's "map of gap year → candidate report" isn't actually written anywhere

You described Step 2 as producing a map you can look at. Today, the candidate list is only computed inside Step 3 at run time (3c_gapfill_3_run_api.py, via index_selected_pdfs + build_candidates) — the closest thing to a file is --dry-run's console printout, which isn't saved. 3b currently only reshapes 3a's output (gapfill_targets, gapfill_skip_reports); it doesn't build the report map at all.

Proposed fix: move the candidate-list computation into 3b (it already has everything it needs: country, gap year, and the skip list), and write it as its own CSV — gapfill_candidate_map_<STAMP>.csv: one row per (gap year, candidate rank), with columns like country, gap_year, rank, candidate_report, offset_years, publication_date, selected_pdf_available. That gives you a real artifact to sanity-check before Step 3 spends any API calls — exactly the "map" you described — instead of only seeing it mid-run.
